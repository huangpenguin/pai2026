机器人系统的性能取决于整条数据路径：相机采集 → CPU 处理与内存搬运 → 网络传输或磁盘保存 → GPU 推理 → 控制输出。训练数据还要求“不漏帧、时间对应正确、设备身份稳定”。HSR 的头部 RGB-D 相机、手部 RGB 相机、六维力／力矩传感器、LiDAR 与全向底盘同时工作时，一个环节堵塞就可能使其他环节拿到过时的数据。

## 1. 从现象定位计算与内存瓶颈

### 1.1 压缩节省存储，却可能耗尽 CPU

> 来源：10.pdf · 第 11–18、27 页。

RGB 图像记录颜色；深度图（depth image／深度画像）记录每个像素对应的距离。深度图压缩后的文件小，并不说明压缩过程便宜。课件中的 ROS 1 案例是：深度图 PNG 压缩让 CPU 紧张，图像发布频率下降；改用适合深度数据的 RVL 后，再确认 CPU 负载、实际图像 Hz、保存量、解码端兼容性和恢复出的像素值。

需要拆开测量**采集、压缩、排队、写盘**。整机 CPU 平均占用不高，也可能某个关键线程已占满一个核；增加 CPU 核数不会自动把串行压缩程序改成并行程序。操作系统可以把线程迁移到不同核，但迁移也不等于同时执行。

> 原课件图仅在 Mac 本地：`assets/10/page-015.png`

图中比较 RVL、JPEG-LS、JPEG-XR、RLGR、PNG：左图压缩比越大，保存得越小；右图毫秒数越小，压缩越快。蓝色是无预处理，橙色是过滤，灰色是量化；量化会改变原来的数值，因此不能把这三组都当作“原始数据完全不变”的同一条件。图出自 Wilson（2017），在 Windows 10、i7-3770K 上进行内存内压缩，**不是讲师机器的实测结果**。它说明应同时比较速度和体积，不能据此保证任何设备上都有相同收益。

计算机的延迟有数量级差异。课件的历史性近似例子为 L1 缓存约 1 ns、L2/L3 约 10 ns、DRAM 约 100 ns、SSD 约 100 μs、HDD 约 10 ms、LAN 往返约 0.5 ms；容量则从 KB、MB 到 GB、TB 增长。这些不是硬件承诺值，其意义是：避免不必要的跨层访问、复制和等待，往往比只看处理器主频更有效。

进程（process／プロセス）通常有独立虚拟地址空间；线程（thread／スレッド）共享同一进程的内存。在启用 GIL 的 CPython 中，多个线程不能同时执行 Python 字节码，但 I/O 等待和释放 GIL 的 NumPy 等原生计算不一定受此限制。ROS 2 的 executor、callback group 和 GIL 共同影响并行性；“单核满载”本身不能证明 GIL 就是原因。可根据测量选择多进程、拆分节点或将热点放到 C++。

> **课件代码：理解视图与复制，不在此运行**
>
> ```python
> b = a[:, :320]  # 视图：通常与 a 共享底层像素内存
> b = a.copy()   # 复制：另分配内存，并读写完整数组
> ```
>
> 第一行修改 `b` 可能影响 `a`；第二行便于独立修改，却增加内存带宽和分配开销。对大图像反复复制，代价会累积到每一帧。

### 1.2 虚拟内存、缓存与 OOM

> 来源：10.pdf · 第 19–22 页。

| 概念 | 机制与诊断意义 |
|---|---|
| 虚拟内存（virtual memory／仮想メモリ） | 每个进程看到自己的虚拟页；内核通过页表映射到物理页。两个进程使用相同虚拟地址，不表示它们使用同一物理内存。页面也可能被换出到磁盘，访问时再通过缺页处理取回。 |
| RSS 与 VIRT | RSS 侧重当前驻留物理内存；VIRT 是虚拟地址空间规模。不能看到 VIRT 很大就断定物理内存耗尽。 |
| 栈与堆（stack/heap／スタック・ヒープ） | 栈保存函数调用等短期状态，随调用返回释放且空间有限；堆承载动态数组等对象，需要管理其生命周期，也可能碎片化。 |
| 页缓存（page cache／ページキャッシュ） | 文件写入可能先进入 RAM 中的缓存，再写入存储设备。短测试很快，不代表持续录制速度也快；脏页积压后可能触发写入节流。 |
| OOM（out of memory／メモリ不足） | 可能是整机耗尽，也可能是容器先达到 cgroup 上限。队列、未释放对象、缓存和数据加载都要纳入检查，不能仅凭宿主机还有空闲内存排除 OOM。 |

持续增长的内存不一定全是泄漏。应区分仍有引用的对象、生产速度超过消费速度的队列、可回收缓存，并比较停止输入后是否回落。检查使用量、限制值、交换空间与进程终止日志，才能知道“哪里不足”。

### 1.3 GPU 利用率、推理显存与训练显存

> 来源：10.pdf · 第 23–26、97 页。

> 原课件图仅在 Mac 本地：`assets/10/page-023.png`

上方 CUDA API 是 CPU 发起调用，下方是 CPU/GPU 间复制、GPU 内核和不同 stream 的执行。应在同一时间轴寻找空隙：GPU 是在等数据、等 CPU 提交，还是正在计算？原图是 NVIDIA 的 GROMACS 示例，并非机器人实测。

`nvidia-smi` 的 GPU-Util 表示采样窗口中至少有一个内核执行的时间比例，**不是全部计算单元被充分占满的比例**。一个并行度不高的内核也可能持续运行；因此 100% 不能独自证明硬件已榨干。配合显存、功耗、温度、时钟以及 `nvidia-smi dmon` 的时间序列观察，再用 PyTorch Profiler 或 Nsight Systems 细分调用、复制与内核。此定义依据 [NVIDIA nvidia-smi 文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

**推理**首先需要容纳参数，再加激活、临时工作区和相关状态。30 亿参数采用 BF16 时，仅权重约为：

$$3\times10^9\times2\ \mathrm{byte}=6\ \mathrm{GB}.$$

这里 GB 用十进制近似；若参数量已包括视觉编码器，不能再重复计入其权重。实际显存大于这个下界。机器人常用 batch size 1，应关注单次延迟；BF16、INT8、`torch.compile`、TensorRT 都是需实测兼容性和效果的优化候选。

课件引用的 RTX 5070 Ti 案例中，模型以约 1 Hz 生成长度为 10 的动作块，动作以 10 Hz 执行，再插值为 100 Hz 关节目标；AiroPi 的另一配置则涉及 10 Hz、长度 10 的动作块。**模型调用频率、动作采样频率、低层控制频率不是同一个量**。Jetson 与工作站的差异还包括可用显存和内存带宽。

**训练**还要保留梯度和优化器状态。课件的混合精度 Adam 示意按每参数 2 B 权重、2 B 梯度、4 B 主权重、8 B 一阶／二阶矩估算，合计约 16 B；30 亿参数即约 48 GB，尚未计入激活等。具体实现、冻结参数或 LoRA 会改变账单，不能把“推理能装下”推成“全参数训练也能装下”。

DataLoader 的文件读取、解压、图像解码也会饿住 GPU；应比较 `num_workers`、数据位置和本地 SSD。多 GPU 训练每步以 all-reduce 聚合梯度，常通过 NCCL，节点内可用 NVLink、节点间可用 InfiniBand。通信与计算重叠能改善效率，但增加 GPU 也增加通信，速度并非线性增长；从 NFS 取数时，单机的数据加载瓶颈会变成集群网络瓶颈。

## 2. 时间同步：能通信，不代表观测属于同一时刻

### 2.1 四种“时间”必须分清

> 来源：10.pdf · 第 30–36 页。

PC 晶振会随温度等漂移，RTC 电池也不是精确同步机制。若相对频率误差为 $d$ ppm，经过 $T$ 秒，未校正偏差近似为：

$$\Delta t\approx d\times10^{-6}T.$$

因此 20 ppm 一天约漂移 1.728 秒，100 ppm 约 8.64 秒。机器能互相 ping 通，只说明某条通信路径可达。

| 时间 | 应用与边界 |
|---|---|
| 系统／墙上时间（wall clock） | 日历时间，可受同步或人工调整影响，可能跳变；Python `time.time()` 属于这一类。 |
| 单调时间（monotonic clock／単調時計） | 适合计算同一机器上的经过时长；Python `time.monotonic()` 的起点没有统一日历含义，不能直接拿不同机器的值相减。 |
| ROS 时间（ROS time） | 可随 `use_sim_time` 使用仿真时钟，也可使用系统时间；仿真暂停或回退会改变其行为。 |
| 设备时间 | 相机、LiDAR 等设备可能有自己的时钟，与主机时钟不是天然一致。 |

同一图像的“曝光／采集时刻”与“主机接收时刻”也不同，USB、缓存、调度会在两者之间加入延迟和抖动。必须确认 `header.stamp` 具体由驱动按何种语义生成。RealSense global time 将设备时间映射到主机时间，但这种映射不等于多相机同时曝光。YUBI 的共同时间基准和 10 Hz 对齐示例，说明训练数据要检验观测与动作是否真正对应。

TF 查询同时依赖坐标系连接关系和指定时刻：缓存中必须有能覆盖该时刻的变换。超出缓存时间范围可能由时钟错位、变换延迟、缺失等造成。讲师回忆的双 PC 导航案例没有保留精确报错，不能将某条特定 TF 错误当作已证实事实。

### 2.2 NTP、chrony 与 PTP

> 来源：10.pdf · 第 31–34、95–96 页。

NTP 利用四个时间戳估计服务器相对客户端的时间偏差：$t_1$ 是客户端发送，$t_2$ 是服务器接收，$t_3$ 是服务器发送，$t_4$ 是客户端接收。

$$\theta=\frac{(t_2-t_1)+(t_3-t_4)}{2},\qquad
\delta=(t_4-t_1)-(t_3-t_2).$$

$\theta$ 为估计时钟偏差，$\delta$ 为扣除服务器处理时间后的往返网络延迟。公式假设去程与回程延迟相等；若不对称，不对称量的一半会混入偏差估计。课件给出的 LAN 约 100 μs–1 ms、互联网数十毫秒等是环境依赖的示例，并非保证精度。

> **勘误：同步不等于定期把时钟瞬间归零。** chrony 通常通过略微加快／减慢系统时钟进行平滑校正（slew），特定配置才使用跳变（step）。课件中的周期归零图和 500 ppm 应理解为简化说明，具体最大校正速率依实现与配置而定。[chronyc 官方手册](https://chrony-project.org/doc/4.8/chronyc.html)

> **课件诊断命令：仅作学习材料**
>
> ```bash
> chronyc tracking
> chronyc sources -v
> ```
>
> 前提是该机器运行 chrony。`tracking` 查看 Reference ID（同步源）、System time（系统时钟与 chrony 所维护 NTP 时间的差）、Last offset（最近一次估计偏差）、Leap status（例如 Normal 或 Not synchronised）。`sources -v` 给出各时间源及字段说明，`*` 标识当前选中源。应在两台 PC 上分别查看，而不是仅看一台出现 Normal 就结束诊断。

> 原课件图仅在 Mac 本地：`assets/10/page-096.png`

PTP（Precision Time Protocol，IEEE 1588）可借助网卡硬件时间戳减少 OS 调度路径的不确定性。在合适的硬件、网络和配置下可达亚微秒级。LinuxPTP 中 `ptp4l` 同步网卡的 PHC（PTP Hardware Clock），`phc2sys` 在 PHC 与系统时钟间同步。图比较的是“常见软件时间戳 NTP”和“硬件时间戳 PTP”的部署，不应读成协议名字本身保证精度；所需网卡及交换机能力要由拓扑和目标精度决定。多相机／LiDAR 的严格采样同步还可能需要硬件触发。相关机制见 [ptp4l](https://www.linuxptp.org/documentation/ptp4l/) 和 [phc2sys](https://www.linuxptp.org/documentation/phc2sys/)。

## 3. 网络与总线：数据多复制一次，负载就可能多一份

### 3.1 带宽、延迟、抖动与排队

> 来源：10.pdf · 第 37–42、48–49 页。

带宽（bandwidth／帯域）是单位时间能传多少 bit；延迟（latency／遅延）是数据到达所需时间；抖动（jitter／ジッタ）是延迟的变化；丢包是数据没有到达。高标称带宽不能保证低延迟，输入速率长期超过出口能力时，队列会使数据越来越旧。

未压缩 RGB 图像的带宽可估算为：

$$R=W\,H\,C\,f\times8,$$

其中 $W,H$ 是宽高，$C$ 是每像素字节数，$f$ 是帧率，$R$ 单位为 bit/s。640×480、RGB 三字节、30 fps 为 221.184 Mbps；两份流约 442.368 Mbps，三份约 663.552 Mbps，尚未计入协议开销。压缩流应使用实际每帧字节数估算。

rviz 为调试再订阅一次图像，可能让机器人跨 Wi-Fi 多发送一份数据，挤压远程操作画面。可在外部 PC **只接收一份跨链路图像，再在外部本地分发**。上传云端与操作画面即使目的地不同，也会争用同一 Wi-Fi 出口；给后台上传限速可能恢复交互及时性，代价是上传结束更晚。

Wi-Fi 通过 CSMA/CA 竞争共享无线信道。其他用户、弱信号、干扰和重传都会占用时间；2.4/5 GHz 环境、漫游、AP 切换也可能改变表现。课件“实际吞吐约标称 50–70%”“漫游可能数秒”的说法是经验量级，不能当作所有设备的固定规律。需要稳定吞吐或低抖动时优先评估有线连接，并在真实负载下测量。

### 3.2 TCP、UDP、分片与 ROS 2

> 来源：10.pdf · 第 44–48、85 页。

TCP 提供可靠、有序的字节流；丢失数据等待重传时，后面的字节可能被有序交付要求阻塞。UDP 本身不保证送达、有序或重传，但 UDP 仍然会经历排队，不能据此保证低延迟。文件、SSH、完整 bag 传输通常重视可靠性；实时图像常需要在完整性与新鲜度之间取舍，应用层的 RTP 或 DDS 配置也参与其中。

| 层次 | 需要检查的问题 |
|---|---|
| 应用层：DDS、HTTP、SSH 等 | 生产／消费队列是否积压，是否重复发送，应用协议如何处理超时和丢失。 |
| 传输层：TCP／UDP | 重传、有序交付或应用补偿是否造成等待。 |
| 网络层：IP | 路由、MTU 与 IP 分片是否符合路径条件。 |
| 链路层：Ethernet／Wi-Fi | 物理速率、无线争用、干扰、重试和共享链路。 |

大消息可能拆成许多传输单元；**IP 分片与 DDS 的消息分块不是同一层机制**。若完成一次消息必须收到 $n$ 个独立、单次丢失概率为 $p$ 的分块，且不补传，则：

$$P(\text{全部收到})=(1-p)^n.$$

课件以约 700 份为例：$p=0.001$ 时约 49.6%；$p=0.01$ 时约 0.088%；$p=0.05$ 时几乎为零。这是说明“大量小损失累积”的模型，不是任意真实链路都独立丢包，也不是说整个大消息必定按 IP 分片发送。实际恢复行为取决于协议。

ROS 2 常见 DDS 配置通过 UDP 多播发现节点，但也有 discovery server 等配置。**发现对端成功与实际数据可达必须分别验证**：网络边界、QoS、数据端口、消息尺寸、共享内存配置都可能影响后者。多机器人同网还会增加发现流量与可见参与者数量，需要按部署划定范围。

### 3.3 PCIe、USB、磁盘和 DMA

> 来源：10.pdf · 第 43、71–72、77 页。

| 课件接口示例 | 理论带宽或标称速率 | 容易漏掉的条件 |
|---|---:|---|
| PCIe 4.0 ×16／×4 | 约 31.5／7.9 GB/s | 通道数、代际、设备及主板连接；GPU 或 NVMe 使用的路径不同。 |
| USB 3.2 Gen 1／Gen 2 | 5／10 Gbps | 相机、线缆、Hub 和上游控制器均需支持。 |
| USB 2.0 | 480 Mbps | 有效载荷低于标称速率。 |
| SATA III | 6 Gbps，约 600 MB/s 的接口量级 | 协议开销和设备持续写入能力。 |
| Ethernet | 1／10 Gbps | 端点、交换机和全路径的最慢环节。 |
| Wi-Fi 6 | 最高标称聚合约 9.6 Gbps | 不是某一机器人客户端的保证吞吐。 |

`B` 表示 byte，`b` 表示 bit，$1\ \mathrm{B}=8\ \mathrm{b}$。DMA（Direct Memory Access／ダイレクトメモリアクセス）允许设备直接在设备与内存间搬运数据，减少 CPU 逐字节参与；CPU 仍需配置传输、处理中断／完成事件及同步。

USB 相机插在不同物理口，也可能共享同一个 Hub 的上游链路。应看 USB 树，不只数插孔。720p、30 fps 的 YUYV 若每像素两字节，需求为 55.296 MB/s，即 442.368 Mbps，已接近 USB 2.0 标称上限并容易超过实际有效带宽。MJPG 由相机压缩后传输，节省 USB 带宽，但主机需要解码。

> **术语澄清：**课件提到 NVENC／QSV 硬件视频处理。编码和解码是不同工作，不能把 NVENC 当作 MJPG 解码器；NVIDIA 将 NVENC 用于编码、NVDEC 用于解码，实际支持格式还取决于硬件。[NVIDIA Video Codec SDK](https://developer.nvidia.com/video-codec-sdk)

长时间录制还需考虑持续写入速度、页缓存耗尽、USB 外置盘断连、SD 卡写入寿命和磁盘空间。`df -h` 查看文件系统剩余容量；实际系统需要容量告警与旧数据转移策略，不能只以刚开始录制时的速度判断。

## 4. 虚拟化：镜像统一了哪些层，又依赖哪些层

### 4.1 VM、namespace、cgroups 和设备可见性

> 来源：10.pdf · 第 51–57、60–63 页。

虚拟机（VM／仮想マシン）在虚拟硬件上运行自己的内核；Linux 容器共享宿主机内核，通过 namespace 隔离进程、网络、挂载等视图，通过 cgroups 约束 CPU 时间、内存等资源。容器轻量和环境可复现，不代表拥有独立内核或天然满足硬实时要求。

> **课件 Compose 片段：绑定目录与发布端口**
>
> ```yaml
> volumes:
>   - .:/workspace
> ports:
>   - "127.0.0.1:${JUPYTER_PORT:-8888}:8888"
> ```
>
> 当前项目目录绑定到容器 `/workspace`。主机端口取环境变量 `JUPYTER_PORT`，未设时为 8888，转发到容器 8888；主机地址限定为 `127.0.0.1`。这解释了本机浏览器访问 Jupyter 的入口，但不自动提供 USB 相机访问，也不自动打通 DDS 发现。

| 课件参数／机制 | 用途、前置条件与预期效果 |
|---|---|
| `--network host` | 在支持的部署中共享宿主机网络命名空间，常见于 Linux；不再等同于 bridge 加某个端口映射。要同时考虑参与者发现和数据通信。 |
| IPC／共享内存配置 | 与网络命名空间不同。通信库使用共享内存时，还需确认相关进程是否真正共享所需资源。 |
| `--device /dev/video0` | 为容器提供指定设备访问；宿主机先要识别设备，容器运行用户仍须满足适用权限。 |
| `-v /dev:/dev` | 映射设备目录；不解决摄像头编号漂移，也不能单凭挂载就推断所有权限已获授予。 |
| `--privileged` | 广泛开放 capability 和设备等权限，并放宽相关安全限制；调试方便但远超单一相机需要。 |
| cgroup CPU quota | 限定一段周期内可消费的 CPU 时间，用完可能被节流，从而增加控制延迟。 |
| `--cpuset-cpus` | 限定可以运行的 CPU 核；仅设置允许核不等于把这些核排他地留给容器。 |
| `--cap-add SYS_NICE` | 允许相关调度／优先级能力；配合实时调度还取决于系统限制、内核和实际配置。 |

> **补充解释：**`--privileged` 不意味着所有 namespace 都消失；未使用 user namespace 时容器内 root 通常对应宿主 UID 0，但受到 capability 等约束；rootless 容器、`--user` 指定非 root 用户也不是一回事。应按设备和 capability 配置实际需要的访问。密钥适合运行时提供，不能误以为放入镜像后再删除就一定从旧层消失。机制依据 [Docker 运行权限文档](https://docs.docker.com/engine/containers/run/#runtime-privilege-and-linux-capabilities)。

宿主机相机能用而容器不能用时，优先比较设备映射、用户及组、驱动接口和容器环境，而不是重新怀疑相机硬件。宿主机空闲内存很多，容器也可能达到自己的 cgroup 内存上限。`docker inspect`、资源限制、OOM／内核日志以及“同输入在宿主机与容器分别测试”的对照能缩小范围。

### 4.2 GPU、实时内核与可复现部署

> 来源：10.pdf · 第 58–65 页。

GPU 内核驱动属于宿主机，CUDA 用户态库可以在容器中；NVIDIA Container Toolkit 将必要设备与驱动能力接入容器。镜像相同仍要求宿主机驱动满足 CUDA 兼容条件。部分深度学习 wheel 自带所需 CUDA runtime，不一定需要另装完整开发 toolkit；但镜像无法把一个不兼容的宿主内核驱动自动修好。

PREEMPT_RT 是宿主机内核特性，不能仅靠容器配置获得。实时策略、`chrt`、CPU 亲和性、IRQ 亲和性等可改变调度表现，仍需在负载下看延迟尾部；平均延迟低不代表最坏情况可接受。

> **课件版本固定示例：仅用于理解配置**
>
> ```text
> python:3.12-slim-bookworm@sha256:…
> uv.lock
> uv sync --frozen
> ```
>
> 镜像 digest 固定具体镜像内容；此处 `…` 是占位，不能直接作为可运行地址。`uv.lock` 记录依赖解析，`--frozen` 使用锁文件而不更新它。还需记录宿主机内核／驱动等镜像之外的信息，并复查相机、GPU 与通信。

集群常限制用户直接运行有 root 权限的 Docker daemon。课件给出的工作流是把 Docker 环境通过 `apptainer build` 转成 `.sif`，再用 `sbatch` 提交 SLURM GPU 作业；Apptainer／Singularity 面向这类环境。命令在此仅表示工作流，真实输入、资源参数和权限由站点规定。训练有队列和时限，需要 checkpoint／resume；home 目录可能容量小、访问慢，scratch 常更快却可能临时清理。AiroPi 示例还涉及 Docker 与 SLURM／PBS 的结合。

部署采用少量机器先试：保存旧镜像、配置和宿主版本，检查设备、通信、数据采集与推理，再扩大范围。保留日志和回滚路径，才能比较升级前后，而不是只知道“换版本后不能用了”。

## 5. 设备管理：设备名、权限、驱动与安全是不同问题

### 5.1 从硬件身份到稳定设备名

> 来源：10.pdf · 第 67–71、80–81 页。

内核识别设备并注册接口；`/dev` 提供用户程序打开、读写的设备节点，`/sys` 暴露设备属性与拓扑，udev 根据属性创建命名和权限规则。`/dev/video0` 通常反映枚举顺序，不能保证重启或重插后仍是同一台相机。

> **课件设备与规则示例：仅作学习材料**
>
> ```text
> crw-rw---- root video 81,0 /dev/video0
> ```
>
> `c` 表示字符设备；`root` 为所有者，`video` 为组，`rw-` 是读写位；`81,0` 是主／次设备号。遇到 Permission denied，要对照设备权限与进程实际 UID／GID／附加组。串口常见 `ttyUSB0`、`ttyACM0` 与 `dialout` 组，但发行版可能不同；GPU 可能涉及 `/dev/nvidia0`、`/dev/nvidiactl`、`/dev/nvidia-uvm`，原始 USB 是 `/dev/bus/usb/001/003` 这类路径，块设备则有 `/dev/sda`、`/dev/nvme0n1`。
>
> ```udev
> SUBSYSTEM=="video4linux", ATTRS{serial}=="HEAD001", \
> ATTR{index}=="0", SYMLINK+="cam_head"
> ```
>
> 该示例选择 video4linux 子系统、父设备链中序列号 `HEAD001`、接口 index 为 0 的节点，并增加 `/dev/cam_head` 链接。图中手部相机另用 `WRIST002` → `/dev/cam_wrist`。序列号和 index 都要由真实 `udevadm` 属性确认，再验证重连后的链接仍指向正确相机；这些占位值不能直接套用到任意硬件。

> **课件诊断命令及读法**
>
> ```bash
> lsusb -t
> v4l2-ctl --list-formats-ext -d /dev/video0
> ```
>
> `lsusb -t` 显示树状 USB 拓扑、驱动和速率，`480M` 与 `5000M` 可帮助发现降速或共享上游。`v4l2-ctl` 的 `--list-formats-ext` 列出格式、分辨率和帧率，`-d` 指定设备。先确认设备及工具存在，再结合相机实际协商结果判断；仅看相机宣传的最高规格不够。

设备诊断按层走：OS 没识别时查电源、线缆、`dmesg`；已识别但名称或权限不对时查 udev 和所属用户／组；宿主机可用而容器不可用时查映射和容器身份；能打开但速率不对时查格式、驱动和总线。

### 5.2 串口、驱动更新、实时性与电源

> 来源：10.pdf · 第 73–77 页。

串口延迟不仅由 baud rate 决定，还包括包长度、USB 转串口缓存和固件处理。例如 100 Hz 控制周期只有 10 ms，往返通信加处理必须留在预算内。FTDI 的 `latency_timer` 会影响缓存等待，主机接收时间也包含这段等待。

> **课件参数／命令说明：不在此调整设备**
>
> ```bash
> cat /sys/bus/usb-serial/devices/ttyUSB0/latency_timer
> dkms status
> dmesg
> ```
>
> 第一行在对应 FTDI／USB 串口路径存在时读取当前延迟设置；改变它应同时比较通信延迟和 CPU 开销。`dkms status` 查看动态内核模块构建状态；`dmesg` 查看内核识别和加载错误。课件还列举 `chrt -f`（FIFO 实时调度策略）、`cyclictest`（测量调度延迟）、`isolcpus`（启动时隔离核相关配置）和 IRQ affinity；这些不是一组可以脱离目标机器直接执行的完整配置。

内核升级可能使 NVIDIA 模块不匹配或 DKMS 重建失败；Secure Boot 也可能拒绝未获接受签名的模块。出现 `nvidia-smi` 无法与驱动通信时，应检查模块加载和日志，不能只重装 Python 包。课件用内核 6.8→6.11 举例：对机器人，自动升级需要与兼容性测试和维护窗口协调。

电源管理也会造成间歇性问题：USB autosuspend、系统休眠后重新枚举、CPU governor 降频、温度限频都会改变时序。课件出现的 `/sys/bus/usb/devices/*/power/control` 值 `on`、CPU governor `performance` 是具体电源配置项；Jetson 的 `tegrastats` 用于观察状态，`jetson_clocks` 涉及时钟配置，`nvpmodel` 涉及功耗模式。改变功耗和时钟前必须理解设备能力、散热和部署目标；性能模式仍不能消除过热降频。

### 5.3 安全停止与数据质量监控

> 来源：10.pdf · 第 79、81、83 页。

硬件急停、固件速度／力矩限制、watchdog 心跳和通信超时停止构成不同层的保护。应使关键停止路径不完全依赖高层 AI 进程仍然健康；层数增加也不等于未经验证就可以保证安全。

yubi-core 示例检查 topic 是否存在、数据是否新鲜、实际 Hz、diagnostics 和 TF。明确启用监控时，pending 阶段 level≥1 会阻止开始；录制中 level 2 会中止／取消录制。这是数据采集的质量控制逻辑，**不能代替机器人安全停止链**。

课件给出的运行前条件包括：时间偏差满足任务阈值、相机固定名称正确、格式／分辨率／fps 正确、USB 实际协商速率符合预期、topic Hz 正常、网络连接方式和负载已确认、磁盘余量足够、关键单核及温度／GPU 正常、镜像和配置版本可追踪、急停与 watchdog 可验证。磁盘至少预留计划录制量两倍是课件示例策略，应根据任务选择余量。

## 6. 用受控实验建立证据

### 6.1 压缩与网络实验的具体含义

> 来源：10.pdf · 第 4、86–93 页。

本课实验使用浏览器、Google 账户、Colab CPU 和已附的资料，不要求本地安装 GPU、Docker、ROS、rviz 或连接实机。必做内容是深度 PNG 压缩与共享网络模型，可选内容是日志／配置判断。以下描述用于学习，不执行课程实验。

**压缩实验：**使用 24 张真实 depth 图及配套 RGB／采集时间，分别测试 PNG level 1、6、9，每组重复三轮，只计压缩时间，并确认解码后所有像素一致。

> 原课件图仅在 Mac 本地：`assets/10/page-088.png`

图中 level 1 约 2–3 ms、约 160 KiB；level 6 约 7–8 ms、约 85 KiB；level 9 中位数约 47 ms、p95 约 53 ms、约 80 KiB。这是教材制作时的本地测量，不能当作当前 Colab／机器人 CPU 的结果，也没有在这张图中比较 RVL。30 Hz 的帧周期为 $1000/30\approx33.3$ ms，level 9 仅压缩就越过预算；level 6 比 level 1 少很多字节，而 level 9 进一步省下的体积较少却显著变慢。即使 p95 小于 33.3 ms，采集、排队、写盘等还需要时间，应测端到端处理和真实输入／输出 Hz。

**网络实验：**使用 15 fps 及共享 FIFO 链路模型，比较仅远程操作、增加订阅与上传、外部中继、外部中继加上传限速。纵轴“画面有多旧”定义为：

$$\text{frame age}=\text{当前时刻}-\text{当前显示帧的采集时刻}.$$

> 原课件图仅在 Mac 本地：`assets/10/page-090.png`

附加订阅与上传时，红线逐步上升到数秒；只中继仍有后台上传竞争，橙线也持续增长；中继加限速保持较低画面年龄。该模型没有模拟 Wi-Fi 丢包、重传、接收处理，不能把曲线当作真实无线测试。

限速实验将机器人→外部的图像降为一份，把上传速率限制在视频需求的 0.2 倍。比较时必须发送**同样多的上传数据**，保留未发送积压直到完成：课件模型中视频延迟 p95 大幅下降，而上传从约 8 秒延长到约 24 秒。否则“丢掉上传数据后更快”并不是公平改善。

扩展练习分别向真实 RGB/depth 时间加入 120 ms 人工偏差；读取 cgroup CPU／内存上限，读不到就标为未确认；依据模拟 `udevadm` 输出写规则但不应用实机；分析复制、页缓存、模拟 CPU/GPU 日志。输出应写清条件、时间、字节数、像素一致性、画面年龄与上传完成时间，并给出一个 validation 指标、阈值依据和失败后的调查位置。

### 6.2 诊断工具要回答具体问题

> 来源：10.pdf · 第 8、27、48、63、80、84 页。

| 问题 | 观察手段 | 对照应保持什么一致 |
|---|---|---|
| CPU 热点 | `htop`、`pidstat` 定位进程／线程；`perf` 看原生热点，`py-spy` 看 Python 调用 | 图像、分辨率、帧率；一次只改压缩等一个变量。 |
| 内存增长／OOM | `free`、RSS、cgroup 限制、内核／终止日志 | 同样输入量、运行时间、队列容量。 |
| GPU 等待 | `nvidia-smi dmon`、PyTorch Profiler、Nsight Systems | 模型、精度、batch、数据位置与预热条件。 |
| 网络及时间 | `iperf3`、topic Hz、chrony 状态与实际帧年龄 | 发送的数据量、订阅者、上传负载、连接方式。 |
| 容器差异 | `docker inspect`、设备／用户／网络／资源限制、版本 | 同一宿主机与同一输入。 |
| 设备异常 | `dmesg`、`udevadm`、USB 树、权限与设备身份 | 同一设备，记录换口／换线／重连等变化。 |

统一方法是“现象 → 测量 → 一个受控改变 → 同条件比较 → 记录”。没有改善的尝试也应记录，以免下一次再次猜同一个原因。

## 7. 习题与逐项解析

以下参考答案由课件知识推导，资料未提供官方答案键。

### Q1　图像处理与 CPU／内存负载

**请选择下列说法中错误的一项。**

- **A.** 反复复制大图像会增加内存读写，有时会影响处理时间。
- **B.** 只要压缩图像使保存体积变小，包括压缩处理在内的 CPU 负载也必然变小。
- **C.** 相机 Hz 降低时，应检查使用 CPU 的进程，并确认压缩等处理的负载。
- **D.** 讲课案例发现深度图 PNG 压缩令 CPU 紧张，因此改成 RVL。
- **E.** 改变压缩方式后，除了保存体积，还要确认 CPU 使用率、图像 Hz 和读取端兼容性。

**提示：**区分数据压缩后的体积和产生压缩数据所需的计算。

**参考答案：B。**

- **A 正确。**复制通常需要读取原数据、写入新缓冲区，并可能分配空间；高分辨率多路图像会消耗可观带宽。实际时间也受缓存、内存和并发负载影响，因此题目用“有时”是合理的。
- **B 错误。**压缩算法是在用计算换存储／传输体积，压得更小可能需要更复杂的搜索或编码。PNG level 9 的示例正是保存量仅略降、CPU 时间却大幅增加。
- **C 正确。**图像 Hz 下降是整条流水线的结果，定位 CPU 热点可判断是否卡在压缩。也应继续检查单线程、输入队列和写盘，不能仅凭频率下降就直接归罪相机。
- **D 正确。**这与课件 ROS 1 案例相符，RVL 是该案例采取的改进。它不是对所有图像和平台的通用优胜结论，替换后仍要实测。
- **E 正确。**体积、速度与兼容性决定新方案能否真正用于系统。若读取端不支持 RVL，或恢复值不符合要求，压缩端再快也不能完成数据闭环。

### Q2　机器人 PC 与外部 GPU 机器的时间同步

**请选择下列说法中错误的一项。**

- **A.** 多台 PC 处理传感器信息时，时钟偏差可能影响使用时间戳的处理。
- **B.** 检查 chrony 同步时，应在两台 PC 上分别确认同步源和状态，而不是只看一台。
- **C.** 应确认传感器时间戳表示测量时刻还是接收时刻，以及使用哪一个时钟。
- **D.** 只要 PC 之间时钟同步，传感器自己的时钟和拍摄时机也会自动一致。
- **E.** 使用 TF 时，确认是否能取得请求时刻对应的坐标变换很重要。

**提示：**主机时钟、设备时钟、采样事件是三个层次。

**参考答案：D。**

- **A 正确。**融合观测、配对动作和查询 TF 都利用时间戳关联事件。时钟偏差可能把本应对应的数据解释成不同时间，或使查询落到 TF 缓存范围之外。
- **B 正确。**一台同步正常不能证明另一台也正常，两台可能使用不同源或有一台失去同步。应比较各自状态与偏差，并按任务要求判断是否足够。
- **C 正确。**接收时间包含通信和调度延迟，与真实采集时间不等价。设备时钟还需映射到共同基准，才能跨传感器直接比较。
- **D 错误。**NTP 同步主机并不自动控制传感器晶振，更不一定同时触发曝光。严格多传感器同步需要确认设备时间映射、PTP 支持或硬件触发等具体机制。
- **E 正确。**TF 要求的不只是“这两个坐标系曾经有关联”，还需要目标时刻的可用变换。时钟正常时也可能因变换发布太慢或缺失而失败，因此要检查具体时间范围。

### Q3　Wi-Fi 远程操作与数据传输

**请选择下列说法中错误的一项。**

- **A.** 远程操作画面和云端的目的地不同，所以即使共用同一 Wi-Fi，也不会发生带宽竞争。
- **B.** 讲课案例中，调试用 rviz 增加图像订阅使通信拥塞，操作画面卡顿。
- **C.** 外部 PC 接收一次图像后再分发到各个画面的中继方式，可以减少机器人的重复发送。
- **D.** 将机器人内保存的数据上传云端时，也应确认与远程操作共享的通信路径负载。
- **E.** 引入上传限速后，应在同样条件下比较远程操作延迟和卡顿是否改善。

**提示：**决定竞争的是共享路径，不是最终地址是否相同。

**参考答案：A。**

- **A 错误。**两种流量在到达不同目的地之前，可能共用机器人网卡、Wi-Fi 信道、AP 和出口队列。共同瓶颈处会竞争带宽，并可能增加视频等待。
- **B 正确。**增加订阅可能增加跨无线链路的图像副本，这是课件案例的原因。调试工具本身也会改变被测系统的负载，所以应把它记录进实验条件。
- **C 正确。**先跨无线发送一份，再在外部局域连接中分发，能减少机器人侧重复图像流。中继仍有处理和下游带宽成本，但把副本移出了关键无线段。
- **D 正确。**本地文件早已录完不代表上传没有实时影响，网络发送仍占用共享资源。检查共享路径可解释“录制正常、开始上传就卡”的现象。
- **E 正确。**需要用相同订阅者、图像与上传总量做公平对照。还要记录上传完成时间，因为交互延迟改善通常以后台任务变慢为代价。

### Q4　Docker 与 Linux 虚拟化

**请选择下列说法中错误的一项。**

- **A.** Linux 容器共享宿主机内核，因此可用内核功能依赖宿主机。
- **B.** namespace 划分进程能看到的进程列表、网络等范围。
- **C.** cgroups 限定内存后，即使宿主机还有空闲，容器也可能发生内存不足。
- **D.** 相机在宿主机可用、容器中不可用时，应检查设备分配和执行用户权限。
- **E.** 分发相同 Docker 镜像就能保证 GPU 工作，不受宿主 GPU 驱动差异影响。

**提示：**镜像主要固定用户态环境，硬件和宿主内核仍在镜像外。

**参考答案：E。**

- **A 正确。**Linux 容器使用宿主内核处理系统调用和设备访问。PREEMPT_RT、内核模块等能力因此不能单靠替换用户态镜像保证。
- **B 正确。**namespace 是对进程可见视图的隔离，不是 CPU 或内存配额本身。资源限额主要由 cgroups 等机制负责。
- **C 正确。**容器自己的限制可以先于整机容量触发回收或 OOM。诊断要读取容器限制与使用量，不能只看宿主机 `free`。
- **D 正确。**宿主成功说明部分硬件／驱动路径已工作，可以继续核对容器是否拿到设备以及实际用户身份。映射了节点但没有适用访问权限，仍然可能 Permission denied。
- **E 错误。**GPU 内核驱动属于宿主机，必须和容器所需 CUDA 用户态环境满足兼容条件。相同镜像减少环境差异，但不能覆盖宿主驱动缺失或不兼容的问题。

### Q5　Linux 机器人设备管理

**请选择下列说法中错误的一项。**

- **A.** udev 规则可根据序列号等能识别设备的属性创建固定名称链接。
- **B.** 出现 Permission denied 时，应对照设备文件的所有者、组、权限与执行用户。
- **C.** 相机一旦被识别为 `/dev/video0`，以后重启或重插仍保证由同一相机获得此名。
- **D.** 多台 USB 相机即使插在不同接口，也可能共享上游带宽。
- **E.** 内核更新后 GPU 不可用时，应检查驱动模块加载与内核日志。

**提示：**枚举顺序、硬件身份、访问权限分别解决不同问题。

**参考答案：C。**

- **A 正确。**稳定的序列号及合适接口属性可把物理相机映射到 `/dev/cam_head` 等用途名。还须验证属性唯一且重连后仍正确，不能只按易变的 video 编号匹配。
- **B 正确。**设备节点的权限要和进程实际 UID、GID、附加组一起判断。容器中的用户名看起来相同，也不能替代对实际身份与授权的核对。
- **C 错误。**`video0` 一般来自枚举顺序，重启、重插或增加设备都可能改变顺序。要保证头部／手部身份，应依据稳定属性命名并进行功能验证。
- **D 正确。**物理插口不同不意味着有独立控制器和独立上行。`lsusb -t` 的树能显示 Hub 和上游共享情况，帮助解释多相机一起使用才降帧的现象。
- **E 正确。**内核更新可能使已有模块失配、重建失败或被签名策略阻止加载。先看 DKMS 状态与内核错误，比仅重装用户态深度学习库更接近问题所在层。

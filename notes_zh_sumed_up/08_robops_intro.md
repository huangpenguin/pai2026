# 第 8 章｜机器人系统工程、MLOps 与 RoboOps

## 1. 从机器人功能走向完整系统

### 1.1 机器人定义与应用边界

> 来源：8.pdf，第 18–19 页。

“机器人”（robot／ロボット）的定义随用途而变化。课件引用的 JIS B 8445 表述强调：两个及以上轴可编程，具有一定自主性，在环境中运动并执行预期任务；NEDO 的工程性定义则强调**传感器、智能/控制系统、驱动系统**三类要素。此处是在转述课件定义，并非判断所有机器人都必须具有同样的外形或移动底盘。

| 类别 | 课件定义与功能特点 | 示例 |
|---|---|---|
| 工业机器人 | 课件引 JIS B 8433：为工业自动化使用，可固定或移动，至少三轴可编程，自动控制、可重新编程的多用途机械手 | 焊接、装配、涂装、搬运机械臂；高速、精确、重复作业 |
| 服务机器人 | 工业自动化以外，为人或设备完成有用任务 | 扫地机器人、Pepper 接待与对话机器人；替代脏、危险或单调工作 |
| 专用机器人 | 依任务定义设计，不能只用工厂机械臂的形态理解 | da Vinci 手术系统、无人机、火星探测车 |

农业采摘案例用于说明：社会需求最终要变成可检验的系统指标，而不仅是一个识别模型。课件以 Artemy（旧名 FARO）为实例；人口与市场统计属于案例背景，这里聚焦其技术设计。

### 1.2 系统工程贯穿硬件、软件与数据的生命周期

> 来源：8.pdf，第 21–28、36 页。

系统工程（Systems Engineering／システムエンジニアリング）从**需求定义 → 设计 → 集成 → 验证 → 运行**俯瞰复杂开发，同时管理硬件（机械、电气）、软件（控制、AI）与数据。它处理的是模块之间的约束：例如相机位置决定可见范围，夹具形状决定可接近空间，视觉延迟又影响机械臂能否及时抓住目标。

采摘案例的三个关键环节是：

1. **需求分析（要件分析）：** 将安全、成本、性能和环境适应性转成指标，并与现场共同确定目标。
2. **架构设计（アーキテクチャ設計）：** 由需求决定机械、电气、软件的组成及主要部件，考虑它们互相影响。
3. **实机验证与反馈：** 先理解农场实际工作，再用数月现场测试暴露问题，将结果返回设计；仿真用于加速，但不能代替现场。

> 原课件图仅在 Mac 本地：`assets/08/page-23.png`

这张需求图把**农场管理**与**机器人性能**放在同一张表：果柄长度、朝向、高度、重叠程度，以及图像识别率、采摘成功率。右图进一步标出净空（clearance）、果柄高度与朝向；朝向示意为 $-45^\circ$ 至 $45^\circ$。表格中的 `xx mm`、`xx %` 等是源图刻意隐藏的参数，不能据此编造真实验收阈值。系统目标要求“有多少果实符合可采条件”和“面对符合条件的果实，机器人成功多少次”都可量化；改善栽培管理也是系统设计的一部分。

> 原课件图仅在 Mac 本地：`assets/08/page-24.png`

图中部件包括采摘手、机械臂、手部相机、固定相机、机器人控制器、工业 PC 和移动底盘。采摘手与底盘承担机械功能，控制器及工业 PC 承担电气/计算功能，相机及其识别软件提供视觉信息。图上的分类是便于讨论的侧重点，实际相机安装、标定、驱动和 AI 推理跨越多种专业。

课件的现场仿真/开发组合包括：WinCAPS III / VRC 机器人开发环境，Linux / Windows 操作系统，C++ / Python，以及 ROS、OpenCV、TensorFlow、PyTorch、OpenVINO。核心思路是把厂商机器人开发环境与开放软件结合，减少重复造工具。团队还需连接设备供应商、软件公司、大学、内部部门、农业人员和海外合作方；共同的需求、接口和测试结果是协作基础。

## 2. DevOps、MLOps 与持续改进的数据流

### 2.1 从串行交付转为并行开发与反馈

> 来源：8.pdf，第 30–34、45 页。

**DevOps** 把软件开发（Development）与运行维护（Operations）持续连接，在短周期内改进。**MLOps** 则将数据、模型训练、验证、部署和运行反馈组织为持续引入与维护机器学习模型的流程。本课题目中的 RoboOps 将这一思路放到实体机器人运行环境，重点仍是模型、软件与现场数据共同形成循环。

课件的开发模式图对比“公司开发一段 → 农场测试一段”的串行流程，与借助 AWS / GitHub 共享数据、知识和软件的并行流程。开发团队、合作公司、大学和农场通过共同平台协作；案例中白天开发、夜间现场测试，使反馈持续流动。远程会议与集中记录减少跨地点等待，但并行开发仍需要一致的数据和软件版本。

模型开发的完整链条是：

**需求定义 → 数据设计 → 采集与整理 → 标注/教师数据制作 → 模型选型与开发 → 训练 → 评估 → 部署使用 → 新数据与改进。**

后期发现问题时，越靠前的错误需要返工的环节越多。例如标签类别定义错误，不是再训练一次即可解决，而可能需要重新制定标注规则、重标数据、再训练并重新验证。课件以数月至一年以上说明项目周期随规模而变化，强调早期构想的价值。

### 2.2 把工具放回它服务的数据环节

> 来源：8.pdf，第 33–34 页。

> 原课件图仅在 Mac 本地：`assets/08/page-33.png`

图中数据流为：现场获得的数据 → 数据存储与标注 → 可训练的数据 → GCP 上训练 AI 模型 → GitHub 版本管理与 CI/CD → 机器人运行。标注代办服务向标注环节提供数据；模型运行又为下一轮产生现场信息。前端的数据定义、采集和标注通常更难完全自动化。

| 工具角色 | 课件示例 | 解决的问题 |
|---|---|---|
| 数据管理与标注 | FastLabel、AWS SageMaker、标注外包服务 | 管理样本和标注规则，组织数据生产 |
| 训练与计算 | GCP、云计算资源 | 运行模型训练与实验 |
| 实验管理 | W&B / WandB、TensorBoard | 比较训练曲线、实验配置和结果 |
| 代码/版本管理与自动测试 | GitHub、GitHub Actions、Jenkins | 组织变更和 CI/CD，自动执行检查 |
| 运行端 | 实体机器人 | 在真实任务中验证结果、持续积累数据 |

**补充解释：** “代码通过测试”“离线模型指标提升”“实机任务成功”是不同层面的证据。把模型部署到机器人之前，需要知道使用了哪一版数据、标注、训练配置和软件；否则现场失败很难定位来自模型还是接口变化。

课件还介绍类似 Kaggle 的团队内或开放数据竞赛：将现场高质量数据存到云端，多个团队共享计算资源进行模型制作与训练，再比较结果、选择优秀模型返回机器人。它同时服务于性能改进、知识积累和人才培养；真正比较的应是同一任务与评估条件下的结果。

## 3. 机器人软件的知识结构：ROS 与 Docker

### 3.1 从应用到底层基础

> 来源：8.pdf，第 36–41 页。

课件用层级图表达软件能力的依赖：顶层是用户看得到的 UI 和模型调用；其下是 ROS / PyTorch 等框架与 NumPy / scikit-learn 等库；再下是 AWS、Google Colab、Azure 等云环境，Python / C++，Git / GitHub 和 Docker；底层是操作系统、文件系统等计算机科学及概率统计、线性代数、微积分。越靠应用越容易立即使用，但范围较专门、变化较快；基础知识迁移范围更广。

机器人开发还涉及 Web、IoT、轨迹生成、自主移动和机械/电气知识，如 3D 打印、EMC 电磁兼容与噪声设计、散热和相机。要点是知道当前问题属于哪一层，而不是把所有故障都当作神经网络问题。

### 3.2 ROS：把机器人能力拆成可以通信的模块

> 来源：8.pdf，第 38–39 页。

ROS 是常见的机器人中间件（middleware／ミドルウェア），用于研究、教育和产业等场景。其主要特点：

- 开源软件生态；使用和分发仍应遵守各包的许可证。
- 以节点（node／ノード）组织模块，支持分布式处理。
- 话题（topic）提供发布/订阅 Pub/Sub，服务（service）提供请求/响应 Request/Response。
- 提供 SLAM、导航、图像处理等软件包；支持 Python、C++ 等语言。
- 可与 Gazebo 等仿真器连接，也可通过驱动连接传感器与执行器。

**补充解释：** 相机节点持续发布图像适合话题；查询某个配置或要求一次计算并等待结果，可以采用服务。ROS 的价值是让不同能力按约定接口组合，而不是保证所有设备接上后都能自动协同。

课件列举兼容生态中的 Roomba、DENSO VS060、Pepper、RealSense D435；相机脚注注明原 Intel 品牌在该课件时点已改为 RealSense 公司。课件说明仍有 ROS 1 包存在，本课程实习主要使用 ROS 2，阅读示例时应分清版本。

### 3.3 Docker：分发一致的应用运行环境

> 来源：8.pdf，第 40 页。

Docker 是创建、分发和运行容器环境的平台。它可用于开发、测试、CI/CD 和生产应用，帮助统一复杂机器人项目的软件依赖。

原图比较了两层结构：虚拟机在 hypervisor 上各自运行客户操作系统，再运行库和应用；容器由容器引擎管理应用及库，不给每个容器配一套独立内核。因此容器通常更轻量。**补充解释：** 同一运行主机上的容器共享内核；“环境一致”主要针对打包的软件，设备驱动、硬件和外部数据仍需匹配。[Docker 官方说明](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

## 4. 图像识别：标签规则、模型和现场任务必须对应

### 4.1 标注规范是需求定义，不只是画框

> 来源：8.pdf，第 43、45–47 页。

课件以番茄采摘说明数据质量的作用：图像中需要区分主茎（stem）、果柄（peduncle）与果实（fruits），因为机械动作依赖的不只是“有番茄”，还包括应该从哪里接近或切断。第 46 页对比重新标注前后对细果柄等区域的分割，展示标签质量本身可能显著改善识别。

第 47 页进一步给出可操作的标注规则：

1. **先定义学什么。** 例如穿着玩偶服的人，算“人”还是不算，必须统一。
2. **定义标到哪里。** 图中被遮挡而人也无法可靠确定的膝盖不强行标注；可见性与标注规则应明确。
3. **保持整个数据集一致。** 前后批次的类别或位置标准不同，会给模型互相冲突的监督。
4. **区分标签与推断。** 在人像这一明确领域积累大量数据后，模型可能学到部位间相对位置，从而推断遮挡位置；这不等于标注员应随意猜测位置。

右图展示 CNN 在密集人群上输出大量检测框，是数据质量影响模型效果的案例；课件未提供独立评估协议，不能仅凭示例图计算准确率。

### 4.2 在真实数据上比较模型，并看懂 mIoU

> 来源：8.pdf，第 48、56–58 页。

课件将模型 A 的 **mIoU 0.49** 与模型 B 的 **mIoU 0.92** 并列，图上 B 对细长果柄的分割更连贯。这些是案例结果，说明选型可能显著影响任务效果；选模型应参考综述、Kaggle 等实践，再在实际数据上验证，超参数调节经验也可借鉴。

**补充解释：** 对类别 $c$，交并比与平均交并比为

$$
\operatorname{IoU}_c=\frac{|P_c\cap G_c|}{|P_c\cup G_c|}
=\frac{TP_c}{TP_c+FP_c+FN_c},\qquad
\operatorname{mIoU}=\frac{1}{C}\sum_{c=1}^{C}\operatorname{IoU}_c.
$$

$P_c$、$G_c$ 是预测与真值中该类别的像素集合，$TP$ 为正确预测该类的像素，$FP$ 为多报，$FN$ 为漏报，$C$ 是纳入平均的类别数。分母是“预测或真值认为属于该类”的区域，因此它同时惩罚漏分和多分；如何处理忽略类、空类别应服从实际评估配置。[TensorFlow MeanIoU 定义](https://www.tensorflow.org/api_docs/python/tf/keras/metrics/MeanIoU)

识别指标不等于采摘成功率：末端定位、夹具接触和控制仍影响最终任务。课件以 SO-101 模仿学习与“AI 识别＋规则式机械臂控制”的演示强调，任务的前提条件比演示看起来流畅更重要；稳定、易调试的经典方法与学习模型组合，有时比一味采用最新模型更实用。

## 5. 遥操作、并行部署与仿真—现实循环

### 5.1 在运行中获得数据，逐渐减少人工接管

> 来源：8.pdf，第 50–51 页。

> 原课件图仅在 Mac 本地：`assets/08/page-50.png`

右图的循环是：专家通过遥操作（teleoperation／遠隔操作）控制机器人 → 收集实际运行轨迹 → 用离线数据学习控制策略 → 在实机测试。左图把它扩展到多个并行环境：各环境汇集数据，更新后的策略再部署回所有环境。

第 51 页按部署阶段展示规模扩大：初期主要由人直接操作；学到策略后，一部分机器人自动完成任务，遇到困难发出 Help 请求，由人接管；继续积累数据、离线学习，再扩展到更多环境。遥操作不仅生产示范，还能在策略失败时帮助持续提供服务。真正制约规模的量之一是人的介入工作量，而不仅是已有多少台机器人。

课件称遥操作数据可成为接近最优的数据。应理解为熟练操作者在合适任务与设备条件下**可能**提供高质量示范，而非所有遥操作轨迹天然最优；延迟、误操作和任务覆盖仍影响数据价值。数据更多也只有在质量、覆盖和学习方法合适时才可能改进策略。

### 5.2 Sim-to-Real 与 Real-to-Sim 是双向校准

> 来源：8.pdf，第 52 页。

课件以 NVIDIA Omniverse / Isaac Sim 说明高速度、逼真渲染和物理计算如何参与机器人开发：先在仿真中生成多样数据，学习基础感知或控制；再将策略部署到真实环境，用实机数据微调（fine-tuning）。反方向则用真实测量调节仿真器设置，使下一轮合成数据更接近现场。

**仿真数据 → 基础策略 → 实机数据 → 策略微调＋仿真参数更新 → 新一轮仿真。**

这就是课件所说的 Real2Sim2Real2Sim…循环。它同时利用游戏/渲染技术、物理仿真和实机反馈，目标是提升鲁棒性；视觉逼真并不代表摩擦、接触、传感延迟等都准确，因此实机验证仍是闭环的一环。

### Q1｜机器人系统工程

以下关于机器人开发中系统工程的说法，选出**错误**的一项。

- **A**：从需求定义到设计、集成和运行进行整体观察，管理复杂开发。
- **B**：在机器人领域，管理硬件、软件、数据三个要素的整个生命周期。
- **C**：需求分析时，需要将安全性、成本、性能和环境适应性等管理指标量化，并共享目标。
- **D**：架构设计将机械、电气和软件当作互相独立的要素，不考虑相互影响。
- **E**：除了仿真，还应在现场验证实机，并将结果反馈到设计。

**提示：** 看一个部件的选择是否会改变其他部件的输入、约束或工作范围。

**参考答案：D。**

| 选项 | 判断与理由 |
|---|---|
| A | 正确。系统工程跨越需求到运行全过程，防止各阶段目标脱节。例如设计时就需要考虑现场如何验证成功率。 |
| B | 正确。机械、电气、控制和 AI 不是全部，训练数据与标注也参与系统行为。模型更新、传感器变更和数据变化都可能引起重新验证。 |
| C | 正确。“表现好”无法直接验收，识别率、成功率及环境允许范围更便于比较。农场管理条件也需要纳入共同目标。 |
| D | 错误。夹具尺寸会改变相机可视范围，算力与延迟会影响运动控制，模块明显相互约束。架构设计要管理这些接口和影响，而非假定独立。 |
| E | 正确。仿真难以完整覆盖遮挡、摩擦、作物变化和实际工作流程。现场反馈能发现假设不成立的地方，并反过来修改需求或设计。 |

### Q2｜DevOps 与 MLOps

以下关于机器人软件/AI 开发的说法，选出**错误**的一项。

- **A**：DevOps 持续连接软件开发与运行，以短周期改进。
- **B**：MLOps 是持续将 AI 模型引入系统并维护运行的流水线。
- **C**：AI 开发反复执行数据设计、采集、教师数据制作、模型开发，以及评估和部署。
- **D**：AI 模型一旦部署到现场就已经完成，基本不再需要追加数据、重新训练或性能监视。
- **E**：云服务和 GitHub 等工具有助于多地点、多团队并行开发。

**提示：** 机器人部署后仍会遇到训练时没有覆盖的现场变化。

**参考答案：D。**

| 选项 | 判断与理由 |
|---|---|
| A | 正确。开发与运行不是一次交接后的两个孤岛，运行问题应回到开发。较短反馈周期有助于持续改进。 |
| B | 正确。模型训练完成只是其中一步，还要评估、引入系统并跟踪使用结果。数据、实验和发布过程共同组成 MLOps。 |
| C | 正确。新环境或错误标签会促使流程返回采集、整理或设计阶段。持续迭代是课件农业案例的核心。 |
| D | 错误。光照、作物形态、相机位置和使用任务可能变化，使原模型退化。应依据监视和评估结果决定补数据与再训练，不能把首次部署当作永久完成。 |
| E | 正确。共享代码、数据和测试结果可以减少地点间的信息等待。课件因此把公司开发与农场测试从串行改成并行工作。 |

### Q3｜ROS 与 Docker

以下说法中，选出**错误**的一项。

- **A**：ROS 是广泛用于机器人开发的中间件，从研究教育到产业都可使用。
- **B**：ROS 具有节点级模块结构，并提供话题、服务等通信能力。
- **C**：ROS 有 SLAM、导航、图像处理等丰富软件包。
- **D**：Docker 可以创建、分发、执行容器环境，有助于建立一致的开发环境。
- **E**：ROS 只支持特定厂商机器人和一种编程语言，且无法连接仿真器。

**提示：** ROS 的功能在于跨模块与设备组合，Docker 则主要组织运行环境。

**参考答案：E。**

| 选项 | 判断与理由 |
|---|---|
| A | 正确。ROS 以通用模块、通信与软件生态支撑多种开发场景。它不是某一种机器人外形或单一任务。 |
| B | 正确。节点把功能拆成模块，话题用于发布订阅，服务用于请求响应。这些接口使感知、规划、控制能够组合。 |
| C | 正确。SLAM、导航与图像处理是课件明确列出的包类型。使用现成包可减少重复实现，但仍要确认接口与版本。 |
| D | 正确。容器将应用依赖组织成可分发的运行环境，可用于开发、测试和 CI/CD。它不意味着各台机器的硬件及驱动也自动相同。 |
| E | 错误。课件列出多个机器人品牌和传感器，且支持 Python、C++ 等语言。Gazebo 等仿真器连接也是 ROS 的常见用途。 |

### Q4｜AI 图像识别开发

以下说法中，选出**错误**的一项。

- **A**：确定标注规范相当于需求定义，标签质量影响模型性能。
- **B**：仅改进标注规则和质量，也可能显著提升图像识别精度。
- **C**：在实际数据上比较有潜力的模型，可能仅改变模型选型就明显改变性能。
- **D**：自行采集数据、制定规则并标注，能通过实践理解数据质量的重要性。
- **E**：始终使用最新 AI 模型最实用，应避免与经典图像处理或规则方法组合。

**提示：** 比较的是现场任务的可用性，而不只是模型的新旧。

**参考答案：E。**

| 选项 | 判断与理由 |
|---|---|
| A | 正确。标签定义了模型需要学习的目标，例如是否把玩偶服人物标成人。定义不一致会产生互相矛盾的监督信号。 |
| B | 正确。果柄等细结构若被漏标或边界不一致，即使模型不变也会受影响。第 46 页正是重新标注改善识别的案例。 |
| C | 正确。课件展示模型 A 和 B 的 mIoU 差异，说明架构与任务的匹配会影响效果。结论仍需在相同评估条件下比较。 |
| D | 正确。亲自标注会暴露类别歧义、遮挡与边界难点。它帮助把模糊的业务想法转成一致、可执行的标注规则。 |
| E | 错误。实用性还取决于速度、调试难度、数据量、硬件和可靠性。课件明确展示 AI 图像识别与规则式机械臂控制组合，经典方法可补足学习系统。 |

### Q5｜数据获取与真实部署

以下说法中，选出**错误**的一项。

- **A**：遥操作获得的数据可以成为策略学习的高质量数据集。
- **B**：即使学习策略失败，只要人可以介入，也可能在继续服务的同时积累数据。
- **C**：收集更多实际运行数据，有可能提高自动策略质量。
- **D**：可以用高速、逼真的仿真器生成多样数据，再用真实数据微调。
- **E**：只要仿真数据足够多，就不再需要真实世界验证或反馈。

**提示：** 数据数量、覆盖范围和仿真误差是不同问题。

**参考答案：E。**

| 选项 | 判断与理由 |
|---|---|
| A | 正确。熟练操作员可提供有用动作示范，为离线学习建立起点。质量仍依赖操作水平、同步与任务条件，因此题目使用“可以成为”很合适。 |
| B | 正确。人工接管可以处理策略暂时不能完成的情况，同时记录新的困难场景。这是课件从一人一机向多环境并行扩展的机制。 |
| C | 正确。真实运行数据可补充训练集没有覆盖的环境或失败类型。题目说的是可能改善，不是无条件随数量增长。 |
| D | 正确。仿真适合快速产生大量变化，真实数据则帮助适配现场。课件还要求用真实数据反向校准仿真参数。 |
| E | 错误。大量数据若来自错误的接触、摩擦或视觉分布，仍不能消除仿真到现实的差距。真实验证与反馈是发现这些差异的必要环节。 |
